# 固定迁移码关联旧账号

状态：2026-11-15 已部署生产。覆盖 PR #17 中默认需要管理员先签发迁移码的页面流程。

## 当前流程

关联旧账号时，填写原手机号、新邮箱、新用户名、新密码及固定迁移码，再获取并填写新邮箱验证码。无需旧登录用户名或原昵称。固定码由服务端校验，区分大小写，不会下发到前端代码。原账号仍登录的浏览器也可沿用登录会话关联。

用户已明确选择使用固定共享码，默认值在服务端配置中设为本次指定的值。可通过 `ACCOUNT_MIGRATION_CODE` 覆盖；显式设为空字符串可禁用固定码路径。知道共享码及目标账号定位信息的人可以关联该账号到自己的邮箱；新邮箱验证仅证明邮箱可用，不构成旧账号所有权证明。

## 旧账号定位

当前生产只读统计显示，5 个现有 CloudBase 账号均未在本地 `User.phone` 保存手机号。用户随后提供的 CloudBase 用户截图中，有 4 组明确的手机号与用户 ID；通过当前 CloudBase 环境与 `cloudbaseSubject` 精确匹配，4 组全部找到本地原账号（3 个 USER、1 个 ADMIN），没有手机号冲突。截图中未显示手机号的用户不补齐、不猜测。

部署前必须先备份当前生产数据库，再把经核对的 4 条手机号写入现有 `User.phone` 字段。私有映射和回填脚本仅保存在 Git 仓库以外的 `/workspace/work/private-migration/`，不提交真实手机号和用户 ID。回填脚本默认只读 dry-run；必须显式指定 `--apply --backup-dir <受保护的当前备份目录>` 才会写入，并要求目录有 `backup-complete` 及 `database.sql.gz`。写入前保存原值，事务内再次校验身份与手机号冲突，条件更新仅修改 `User.phone`。

部署前 dry-run 确认计划更新 4 条；完整备份验证后已事务回填 4 条。回填后复查 4 条匹配、剩余更新为 0。服务端按手机号定位原账号，支持国内号码、`+86` 和带空格的 `+86` 三种已有存储格式。匹配不到或匹配多个不同用户时拒绝，不能用昵称代替手机号。账号必须属于当前 CloudBase 环境。

## 数据与兼容

固定码仅用于获取服务端签名的邮箱迁移挑战，不会跳过邮箱验证码、提供方邮箱与用户名核对、事务行锁和身份条件更新。完成后保留原 `User.id`、角色和相关作品、空间、管理权限；原 CloudBase 身份不再映射到该本地用户。旧挑战不能重复提交。固定码本身按用户要求复用，不是一次性授权。

前端移除了管理员迁移码生成入口。此前已签发的管理员审批及其后端接口继续保留原有效期和用途约束，以兼容已开始的流程。没有增加依赖、数据库字段或执行生产迁移；本轮仅回填 4 条已确认的 User.phone 并发布代码，没有发送真实验证码或执行真实账号迁移。
