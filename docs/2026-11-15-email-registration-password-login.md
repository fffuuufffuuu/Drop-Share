# 邮箱注册、密码登录与旧手机号账号关联

状态：功能开发与隔离测试完成，待 PR 审阅。未部署生产，未执行生产数据库操作。

后续开发调整：旧账号关联默认改用固定共享码，页面不再要求管理员先生成迁移码；该调整已于 2026-11-15 部署，4 个旧账号的手机号映射经核对后回填。详见 [固定迁移码关联旧账号](2026-11-15-fixed-migration-code.md)。下文保留 PR #17 原始流程与验证记录。

## 用户行为

- 默认登录方式为用户名/邮箱加密码，移除手机验证码登录入口。
- 新用户注册必须填写邮箱、邮箱验证码、登录用户名、密码及确认密码；用户名为 5–24 位英文字母、数字、下划线、点或短横线，以字母或数字开头。密码沿用 CloudBase 的 8–64 位大小写字母、数字、特殊字符要求。
- 邮箱验证码仅用于注册不存在的邮箱，不再把验证码登录当作省略用户名或密码的注册捷径。旧短信接口和原来的注册补填接口返回 410。
- 登录用户名保存在 CloudBase，作品昵称仍保存在本地 User.username，可继续修改为中文昵称。账号设置显示登录用户名；修改昵称不会修改登录凭据。
- 账号设置的身份验证改用已绑定邮箱，不再发送短信。只有手机号的旧账号会获得关联新邮箱的引导。
- “关联旧账号”位于登录页第三个入口，支持 `/login?mode=migrate` 及旧 `/login?mode=link` 地址。填写原手机号、新邮箱、新用户名、新密码并验证邮箱，成功后仍使用原 User.id，保留角色、作品、空间与管理权限。

## 旧账号归属证明

手机号是公开标识，不是密码；不能仅凭输入手机号就重设他人账号。支持两种证明：

1. 原账号仍登录：服务端验证原 CloudBase access token、不可变 sub、本地映射和原手机号一致。
2. 已退出且无法接收短信：在后台“旧手机号账号迁移审核”中，由本地 ADMIN 通过可信渠道人工核实申请人的身份，填写原账号昵称/用户名、原手机号及新邮箱并明确确认，生成 15 分钟有效的迁移码。知道手机号、昵称或公开作品链接本身不足以通过人工审核。

迁移码签名绑定环境、原本地用户 ID、原 CloudBase sub、原昵称、手机号和新邮箱，且只能用于迁移用途。邮箱验证码挑战不能延长人工审批有效期。最终操作通过事务锁和条件更新替换身份映射；成功后原 sub 不再映射到本地账号，因此旧会话和迁移码不能继续领取该账号。重复迁移、用户名冲突、不同身份、验证码用途/环境替换均拒绝。

人工审批由既有管理员权限保护，不接受浏览器声称的角色。若所有管理员会话均失效，需由有权限的运维人员在正式变更流程中恢复管理员访问，不提供公开绕过入口。本次未执行此类操作。

## 提供方与数据边界

沿用 CloudBase HTTP API 和现有 refresh/logout 会话管理，没有引入新依赖、SMTP 密钥或数据库字段。

| 操作 | 提供方调用 |
| --- | --- |
| 邮箱注册发码 | `POST /verification`，email + `target=NON_USER` |
| 校验邮箱 | `POST /verification/verify` |
| 注册用户名及密码 | `POST /signup`，经服务端挑战确认的 email、verification_token、username、password |
| 密码登录 | `POST /signin`，username 或归一化后的邮箱 + password |
| 校验身份 | `GET /user/me`，核对 sub、邮箱与注册用户名 |

官方契约：[注册](https://docs.cloudbase.net/http-api/auth/auth-sign-up)、[密码登录](https://docs.cloudbase.net/http-api/auth/auth-sign-in)。

旧手机号身份不能在没有短信二次验证时通过普通用户接口直接重设，所以迁移以新邮箱注册新的 CloudBase 身份，再原子更新原本地账号的映射。原 CloudBase 身份仍保留在提供方，本地数据不合并或删除。新邮箱必须尚未被使用，不自动抢占或合并其他邮箱账号。

CloudBase 注册和本地 MySQL 不构成跨服务事务。如果提供方注册成功、随后本地数据库提交失败，应按错误联系管理员核对两侧身份，不能将失败当成迁移成功，也不要直接创建空账号领取旧数据。

正式上线前仍需在提供方控制台确认邮箱验证码和用户名密码登录已启用，并由用户使用测试邮箱验证真实收信、验证码和密码策略。本次只做隔离开发验证，未发送真实短信或邮件，未修改生产配置；不会接入尚在申请的微信登录。
